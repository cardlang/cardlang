# The CardLang Guide

A guide that teaches CardLang by example, for programmers who want to write applets. It is published at **[cardlang.github.io/cardlang](https://cardlang.github.io/cardlang/)**, and its chapters read here too:

- [Introduction](docs/index.md)
1. [Getting started](docs/01-getting-started.md)
2. [Values and types](docs/02-values-and-types.md)
3. [Control flow and scope](docs/03-control-flow-and-scope.md)
4. [Functions, references and views](docs/04-functions-references-views.md)
5. [Outcomes](docs/05-outcomes.md)
6. [State that survives](docs/06-state.md)
7. [Talking to the host](docs/07-host.md)
8. [Using the platform](docs/08-platform.md)
9. [Testing and debugging](docs/09-testing-and-debugging.md)
10. [A real applet](docs/10-a-real-applet.md)
11. [Coming from C or Java Card](docs/11-coming-from-c.md)
- [Platform reference](docs/reference-platform.md), generated by `tests/guide_reference.py`

The guide is not normative: the [specification](../language/spec/00-index.md) is.

## Building the site

The site is built with MkDocs and the Material theme, from the repository's uv environment (`uv sync` once). From the repository root:

```bash
uv run mkdocs serve -f guide/mkdocs.yml
```

serves a live preview, and `uv run mkdocs build --strict -f guide/mkdocs.yml` builds it into `guide/site/`. GitHub builds it on every change to the guide, and publishes it from `main` (`.github/workflows/guide.yml`). <!-- linkcheck: ignore -->

CardLang and scenario code is highlighted by the package's own Pygments lexers, in `src/cardlang/highlight.py`. Use `cardlang` and `scenario` as the language of a fenced block.

## Every example is checked

`tests/guidecheck.py`, run by `tests/run_checks.py` and by GitHub, checks every `cardlang` and `scenario` block. A comment on the line before each block says what it is:

| Comment | The block |
|---|---|
| `<!-- check: program NAME -->` | Top-level declarations of the program `NAME`. They carry over: a block continues the program from every earlier block of that name, in this chapter and earlier ones, and a declaration with the same name as an earlier one replaces it. So a chapter shows only what changed. The program must compile at the end of each chapter that shows it. Add `binding=iso7816` for the ISO 7816 binding (the default is raw) |
| `<!-- check: program NAME remove=A,B -->` | As above, after first removing the earlier declarations `A` and `B`, for when the text tells the reader to delete them |
| `<!-- check: fragment -->` | A fragment that must compile |
| `<!-- check: error CE-XXX-n -->` | A fragment that must fail with exactly that error. Its fence carries `title="Does not compile: CE-XXX-n"`, and no other block may. With `binding=iso7816` or `binding=raw`, the block is a whole applet, built for that binding |
| `<!-- check: scenario NAME -->` | A scenario for the program `NAME` as it stands at that point, run on the reference interpreter and the Python VM |
| `<!-- check: excerpt PATH -->` | Lines quoted from the repository file `PATH`, such as `examples/fido2/ctap.card`. Each run of lines must appear in the file exactly, in order; a line `// ...` on its own stands for lines left out |
| `<!-- check: none -->` | Shown, not checked. Use it rarely |

A block without a comment fails the check. A block indented inside a list item is checked too, with its comment indented the same way.

## Writing for the guide

- Talk to the reader as "you", in a conversational tone. Contractions such as "you'll" and "isn't" are fine, in moderation.
- Show, then explain: a short piece of code first, then what it does and why.
- Explain in paragraphs. Use a list only for things that really are a list, such as steps to follow in order, and don't open list items with a bold phrase.
- Vary the sentences. Prefer two sentences, or "because" and "so", to a colon followed by an explanation, and say a consequence where it belongs rather than in a separate "That is why…" sentence.
- Leave out words that add nothing, such as "exactly", "whole" and "deliberately".
- Let each chapter open in its own way, and end when its content ends. There are no fixed opening phrases and no end-of-chapter exercise lists.
- Name the rule the first time it matters, as in *EXP-2*, and leave the exact wording to the specification. Every rule cited is checked to exist, but read it before citing it, to be sure it's the right one.
- Grow the running example, the vault, rather than inventing a new program for each feature, unless a small fragment makes the point better.
- Describe the language as it is, in plain words, with no history of how it came to be.
- Compare with other languages only in chapter 11. The other chapters explain CardLang on its own terms.
- Say when code is wrong. An example that doesn't compile is titled `Does not compile: CE-XXX-n`, which guidecheck enforces. An example that compiles but is wrong on purpose is titled `Contains a bug` and checked with `none` (or written in another language, as in chapter 11). The site draws both titles in warning colours. Either kind is followed by the correct version when there is one.
- Stay independent of the host system. Commands are the toolchain's own (`uv run …`, `clc …`), not shell scripts, and no compiler or build setup of the toolchain is named.
