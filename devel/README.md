# Development aids

This folder holds how CardLang was built: the work-package plans, the reports written along the way, and the scripts used to produce and measure things. None of it is needed to use the language or its tools. It is kept as the record of why things are the way they are, and of how they were checked.

**Paths are as of writing.** A plan or report names files where they were when it was written, and some have moved since. The link check (`tools/checkers/linkcheck.py`) resolves those old paths through the table of moves in `tools/checkers/layout.py`, so every reference is still checked; the table also says where each file went.

| Folder | What is in it |
|---|---|
| [`plans/`](plans/) | The plans of plans: [specification](plans/specification-plan-of-plans.md), [VM](plans/vm-plan-of-plans.md) and, in `release/`, the plan for making the repository public. One detailed sub-plan per work package, by area: `spec/` (the specification and the Base Profile), `vm/`, `tooling/` and `release/` |
| [`reports/`](reports/) | Measurements of the prototype and C VMs and of the bytecode revisions, the FIDO2 and PIV findings, step notes, and the SP14 consolidation report |
| `generators/` | Scripts that write conformance tests and the generated parts of the specification |
| `history/` | One-off scripts that built the decision register and the annexes, kept as a record |
| `measure/` | The measurement scripts behind the reports |

## `generators/`: conformance-test generators

`spN_tests.py` writes the conformance tests of sub-plan N. Each one extracts the code blocks from its chapter, and verifies that every test path referenced in the chapter exists and matches. Re-running a generator overwrites its tests with content regenerated from the chapter. Use this after editing a chapter example.

```bash
uv run python -I devel/generators/sp6_tests.py .
```

The tests of SP3 (`typ-*`) and SP4 (`cex-*`) were generated by inline scripts that were not saved. Those tests are maintained directly in `conformance/`.

`sp14_tests.py` writes the tests added in SP14 for rules that had none. They are referenced from several chapters, so the script lists them in `sp14_owned.txt`, and the chapter generators skip them.

Two generators maintain generated parts of `spec/`:

- `coverage.py` writes Annex D §D.3, the rule coverage matrix, from the test headers plus a curated list of tests that exercise rules without citing them, and the reasons for rules no test can check. It fails if a rule has neither.
- `rule_index.py` writes the index of rules in `00-index.md`.

Run both after adding tests or rules.

## `history/`: one-off bookkeeping scripts

These scripts were run once, to build the decision register, Annex C and Annex D. They are kept as a record of how those files were produced. For example, `gen_register.py` shows how the DN §2 decision table was copied verbatim into `D-001`…`D-135`.

**Do not re-run them.** They append rows and would duplicate entries. The SP14 scripts (`sp14_ce_rules.py`, `sp14_reverse_links.py`, `sp14_annexA_index.py`) completed the compile-error tables, added the missing D.2 links and wrote Annex A §A.3. `speccheck.py` now checks what the first two produced.

## `measure/`: measurement scripts

| Script | Measures | Report |
|---|---|---|
| `pyvm_measure.py` | The prototype compiler and VM: sizes, opcode frequencies, stack depth, budget | `reports/VM5-measurements.md` |
| `revision.py` | Code size, step by step through a bytecode revision | `reports/VM7b-measurements.md` |
| `cvm_measure.py` | The C VM: `sizeof(cl_vm)`, code size per target, the C stack, speed | `reports/VM7-measurements.md` |

```bash
uv run python -I devel/measure/revision.py .
uv run python -I devel/measure/cvm_measure.py > measurements.json
```

`cvm_measure.py` needs the C VM built first (`vm/c/build.py all`).
